= E0-12: Outcome route and observation identity decision
:toc:
:date: 2026-11-23

Status: owner direction APPROVED on 2026-11-23. Jonathan approved the
recommended single fleet admission and correlated-rescan direction. The
original bounded producer patch and counterexample below remain historical
evidence. The follow-on defines actual versioned delivery; complete E0-12,
post-fix state attribution and production operation still require their
acceptance evidence. Production dispatch remains quarantined.

== Approved direction

Adopt the existing trusted fleet importer as the sole admission path for a
producer-identified attempt. Retain Hypatia's rescan as evidence about that
attempt, with explicit correlation and at most one effective contribution to
learning per attempt. The current direct callback must cease creating an
additional independent qualified attempt for the same dispatch.

The owner approved this contract direction after reviewing the counterexample
and the conflict with the May mandatory recording call. The follow-on amends
that contract explicitly. Approval is not a claim that route implementation,
observation state binding or qualification revision machinery is complete.

The bounded v1 uses `attempt_contract = "fleet-attempt/1"`, delivers directly
to the configured fleet feed, and suppresses independent direct recording for
identified attempts. The consumer stores its own versioned admission and
correlated observation. Mutable post-fix state is not yet bound: a later clean
or adverse scan is retained only as unbound audit evidence. Failed/incomplete
attempts retain their existing qualification criteria. This limitation is
required to avoid attributing a later repair's effects to an earlier attempt.

The matching consumer must be deployed and configured before any producer
activation. An older E0-11 reader ignores the new marker and can still credit
a producer `verified` row under its historical interpretation. The version
field alone cannot make that older reader refuse it. Quarantine remains the
activation boundary.

Pair the actual configured roots, not only the code versions: Hypatia's fleet
root must resolve to the producer's `FLEET_ROOT`, and its `HYPATIA_REPOS_DIR`
must identify the same repository root as `REPOS_BASE`. The real learning store
must be named by `HYPATIA_VERISIM_DATA_PATH` where configured. A runner cannot
prove the roots of another process whose configuration was not supplied.

The direct call also emits an echo marked `bot=hypatia`; the importer skips
that echo. The echo alone is not the duplicate-credit defect demonstrated
below. Its missing event ID is an additional existing gap against ruled R6;
this patch does not silently repair that separate path.

The raw monthly file and the qualified consumer store must not be treated as
interchangeable. Code inspection indicates that publishing the same producer
ID into both raw and admitted rows within the receipt lookup's store can make
lookup depend on row order:
https://github.com/hyperpolymath/hypatia/blob/d158aed87f76b93e4f291e995bef9f26559c7fb2/lib/hypatia/receipt.ex[`Receipt.locate/2`]

implementation, not an additional executed counterexample.
The selected route must separate transport mirrors from the canonical
learning ledger, not merely add a third write.

== Executed counterexample

The producer fixture uses the real canonical Mix generator and an inert
throwaway fixer. It emits two distinct failed attempts and their exact
primary/central copies. The wire witness transfers those bytes explicitly to
the importer and passes three checks: identity/mirror fidelity, start exclusion
and replay-safe import, and absence of implicit qualification for raw monthly
rows. This is compatibility evidence, not automatic delivery.

`tests/hypatia-route-counterexample.exs` then takes one actual emitted failure,
calls the actual `Mix.Tasks.Hypatia.RecordOutcome` task with its labels, verifies
that the echo imports nothing, and explicitly appends the producer row to the
importer's feed. On the pinned Hypatia base it reports:

== Approved ruling: one attempt admission, correlated rescan evidence

. Use the trusted E0-11 fleet import as the canonical admission path for
  producer-identified dispatch attempts. The source is append-only; primary
  and central transport copies remain one attempt. Mirrors live outside the
  canonical learning store and never create extra admitted trials.
. Retain rescan verification, but change the current mandatory recording
  callback into a verification/evidence step for that admitted attempt. It
  must not independently record another qualified attempt. Revise the May
  callback contract explicitly as part of implementation.
. An attempt's ID, an observation's ID and a qualification revision's ID have
  distinct meanings. Bind any separately stored rescan observation to the
  attempt through a restricted, source-bound contract. A public caller's
  syntax-valid UUID is insufficient provenance.
. Derive at most one current contribution per attempt. Multiple observations
  are evidence for that contribution, not additional successes, failures or
  qualified false positives. Preserve the existing separate false-positive
  accounting.
  Conflicting observations must use an explicit qualification/retraction rule
  and preserve the history. E0-35's withdrawal work remains a dependency;
  approval of this direction does not claim that machinery is implemented.
. Do not silently reuse `parent_event_ids` for an unruled relation. D7 defines
  that field for receipt revision ancestry. The detailed observation/attempt
  correlation and its relation to D7 must be written and reviewed before code
  relies on them.
. Preserve legacy rows and uncertainty. Do not infer common attempt identity
  from equal content, timestamps or recipe names: two identical attempts may
  be distinct. Historical reconciliation needs its own evidence and receipts.

The invariant can be stated without inventing new mathematics: count effective
attempt qualifications, not raw rows or observations. A single attempt may
contribute at most one effective qualified contribution -- success, failure
or qualified false positive -- or none, under the existing gate. Qualified
false positives retain their current separate accounting, as implemented by
https://github.com/hyperpolymath/hypatia/blob/d158aed87f76b93e4f291e995bef9f26559c7fb2/lib/outcome_tracker.ex[`OutcomeTracker.qualified_outcome_counts/1`].
A later authorised revision changes that effective contribution without
erasing prior evidence.

=== Alternative: make a new restricted direct recorder the sole ingress

The direct route could instead become an idempotent trusted producer-admission
API, while fleet files become audit-only for those events. This preserves more
of the current invocation shape, but requires new admission/provenance and
offline/replay machinery and an explicit restriction on E0-11. Adding a public
`--event-id` option is not that machinery: `OutcomeTracker.record_outcome/5`
deliberately strips caller identity to prevent forged replay/receipt identity,
and the current qualification fold counts rows even if their IDs agree.

The importer option reuses the existing persisted producer identity, source
hash and replay controls and is recommended. Neither option is activated by
the bounded NS-02 producer patch.
