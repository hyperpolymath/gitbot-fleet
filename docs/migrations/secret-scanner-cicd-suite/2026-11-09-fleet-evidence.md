## Receipt scope and runtime dependencies

The source-derived lock closure and `lock-closure-receipts.tsv` authenticate the reusable workflow and its `actions/checkout` edge; they do **not** establish complete runtime provenance or guarantee the contents or availability of a hosted runner. The pinned reusable checks out the suite implementation at the caller's commit and invokes `actions/secret-scan-check/{install,control,check}.sh` and `config/gitleaks/estate-baseline.toml` from that checkout. The installer downloads the Linux x64 Gitleaks 8.30.1 release archive from GitHub, verifies SHA-256 `551f6fc83ea457d62a0d98237cbad105af8d557003051f41f3e7ca7b3f2470eb`, and extracts the executable. The execution also relies on ubuntu-24.04, Git, Bash, yq, Python 3, curl, tar, core utilities and the checked-out subject/configuration and complete Git ancestry. These runtime inputs are not enumerated or independently attested by the current `uses:` receipt. Controls, checksum verification, full-history checks and subject-binding checks are valuable but are not a complete runtime supply-chain receipt.
