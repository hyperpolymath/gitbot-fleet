= Scanner cutover: pons-asinorum and panic-attack → ponsbot and panicbot
:toc: left
:toclevels: 2
:revdate: 2026-11-12

Status: **DESIGN, with the owner's rulings of 2026-11-12 recorded (§8). Phase 0
(the adapters) is the only phase started.** Nothing has been cut over: no
workflow, enrolment manifest, grid row or direct lane has changed. Each later
phase lands as its own pull request.

== 1. Goal

Retire the estate's *direct* invocations of the two deep scanners,
`hyperpolymath/pons-asinorum` and `hyperpolymath/panic-attack`, so that each
one reaches a pull request, a sweep or a gate only through its fleet adapter:
`panicbot` (exists) and `ponsbot` (phase 0 adds it).

The bots are estate tooling. External users do their own scanning for now; this
cutover is not a service offered to them.

=== 1.1 What "retire" means here (decided, §8 D0, 2026-11-12)

The scanners stay as **external engines**. The adapters call them as pinned
subprocesses, which is how `bots/panicbot/src/scanner.rs` already uses
panic-attack. This reading follows the thin-adapter guardrail in
link:../../bots/README.adoc[`bots/README.adoc`]: a bot slot must not absorb a
standalone product. What retires is every *lane* that installs and runs a
scanner binary itself and renders its own row, envelope or gate.

The other reading, that the scanner repositories themselves retire and their
analysis moves into the bots, conflicts with the guardrail and was **not
taken**: the owner ruled on 2026-11-12 (D0) that pons-asinorum and panic-attack
stay as external engines and repositories, and only the direct CI lanes retire.

=== 1.2 Why

* **Double reporting.** standards' enrolment manifest leaves panicbot out with
  the reason _"panic-attack assail already reports in this lane directly;
  panicbot would show the same tool's findings a second time"_
  (`metadatastician/standards` `.gitbot-fleet/enrolment.json`). The direct lane
  is in the way of the adapter.
* **Pins in many places.** panic-attack is pinned separately in at least four
  workflows across three repositories (see §2), and kept equal by comment and
  convention.
* **No adapter for pons.** pons reaches the grid only as a permanent
  hard-wired row, with no fleet member behind it.

== 3. Target state

* The verdict grid has **one** permanent row, Hypatia. panic-attack and pons
  reach it as fleet rows, `panicbot` and `ponsbot`, through
  `scripts/fleet-report-back.sh` and the report-back envelope
  (link:../REPORT-BACK.adoc[`docs/REPORT-BACK.adoc`]).
* Each repository's `.gitbot-fleet/enrolment.json` says whether panicbot and
  ponsbot apply, with a reason when not. "Permanent" stops being hard-wired.
* Each scanner has **one** pin, held by its adapter (`bots/<bot>/canon/pin.toml`)
  and read by every workflow that builds it.
* **pons gates; panic-attack does not** (§8 G1, G2). ponsbot's row is a gating
  row: pons `error` keeps its blocking meaning, now read from ponsbot's row
  instead of the scanner's output. panicbot's row is advisory, so
  panic-attack's findings never block a merge through the fleet. The grid reads
  a row's gating from the enrolment's per-reporter `gating` boolean (standards
  `scripts/lib/verdict-grid.jq`), not from the envelope: enrolments set
  `"gating": true` for ponsbot and leave panicbot without it.
* Hypatia's estate rescan and bridge gate are decided separately (§8 D4); they
  are not PR lanes.

== 4. ponsbot (new adapter)

A thin crate in `bots/ponsbot/`, the same shape as panicbot:

* `BotId::Ponsbot` in `shared-context/src/bot.rs`, added to `all()` only once
  the adapter ships.
* `ponsbot --format json scan <dir>`: runs `pons` as a subprocess at the pinned
  commit, prints a JSON findings array to stdout, writes nothing into the
  scanned tree. That is the report-back driver's contract for a new member.
* `bots/ponsbot/canon/pin.toml`: pons commit and sha256 of pons' published
  rule table, if it has one. Same re-pin procedure as panicbot.
* **Evidence class is carried, not dropped** (decided, §8 D1, 2026-11-12). Each
  finding keeps pons' tier and evidence class. SPECULATIVE findings are
  carried, never dropped, with an explicit class the grid never grades as
  blocking: ponsbot does not pass `--no-speculative`, and caps a SPECULATIVE
  (or unrecognised) class at severity `info` while keeping pons' own severity in
  `pons_severity`. A heuristic never reads as a proof (pons ADR-0004): its
  message says so.
* **Exit codes map to report-back status, never to a pass.** pons exit 1 with
  findings → `ran`. Exit 2 (invalid input, no applicable input, config error)
  → `error` with pons' message as `reason`. A missing binary → `not_run`.
  The adapter prints a findings array only when pons really ran; otherwise it
  prints `{"status": "error"|"not_run", "reason": "..."}` and exits 2 or 3. It
  also refuses a pons binary whose own `tool.source_commit` is not the pin, or is
  absent, as `error`.
* `.ponsignore` and `pons.toml` stay pons' business. The adapter passes the
  repository root and adds no exception mechanism of its own.
* Driver integration: one `case` arm in `scripts/fleet-report-back.sh`, one stub
  in `tests/fleet-report-back-test.sh`, one build in
  `scripts/fleet-report-back-build.sh`, as `docs/REPORT-BACK.adoc` prescribes for
  a new adapter.
* SARIF: the deep-recon lane uploads pons SARIF to code scanning. Either the
  adapter gains `--format sarif`, or the lane keeps a SARIF conversion step fed
  from the adapter's JSON. Pick one in phase 3.

== 5. panicbot changes

* Make `bots/panicbot/canon/pin.toml` the single panic-attack pin. Today it pins
  only the rule-ID table; it gains the build commit, and the workflows read it
  instead of their own `PANIC_ATTACK_SHA` or `PA_SHA`. *Phase 0:* the `[build]`
  table is added (value and provenance in the file; workflows do not read it
  yet, see §8 D7).
* Parity with the direct lane's envelope. The direct lane distinguishes
  "not installed", "timed out", "exited non-zero" and "exited 0 without a valid
  report", and checks `weak_points` and a positive `statistics.total_lines`.
  panicbot `scan` must surface each of these as `error` or `not_run` with a
  reason, never as an empty `ran`. *Phase 0:* tests added in
  `bots/panicbot/tests/envelope_parity_test.rs` and the driver tests. They found
  three cases that read as `ran` or hung, now fixed at the source in
  `bots/panicbot/src/scanner.rs`: the timeout was never enforced (a hung scan
  hung), a non-zero exit with parseable stdout was accepted, and a report with
  no `statistics.total_lines` (nothing analysed) was an empty `ran`.
* Scope excludes: the direct lane counts excluded findings separately
  (`counts_excluded`). Decide whether the adapter reports them or the grid's
  scope filter alone handles them.
* Fix or retire `panicbot-sweep.yml`'s install line (see §2.2).

== 7. Risks and rollback

* **Reusable-workflow callers.** `hypatia-scan-reusable.yml` is called estate-wide.
  Removing the `panic-ref`/`pons-ref` inputs breaks callers that pass them.
  Deprecate first (accept and ignore with a warning), remove a cycle later.
  `propagate-workflow-pins.sh` is the propagation path.
* **Silent green.** The main hazard is an adapter that runs nothing and reports
  an empty `ran`. The parity cases in phases 0 and 3 exist to catch this.
* **Gate drift.** Fleet rows grade by normalised severity
  (`error` → high, `warning` → medium). pons' `error` must keep its blocking
  meaning through that normalisation and through the enrolment's
  `"gating": true` (checked by `tests/fleet-report-back-test.sh` against the
  real renderer when `STANDARDS_DIR` is set; re-check before phase 2).
* **Callers that opted into block-on-critical.** Under §8 G2 panic-attack no
  longer blocks, so a caller that set `block-on-critical` loses that block when
  phase 2 lands. Deprecate the input (accept, warn, ignore) a cycle before
  removing it, and say so in that phase's PR.
* **Rollback.** Phases 2 and 3 are reverts of their own PRs. Phase 1 is
  additive. Keep the deleted steps' last commit SHA in each PR body.

== 8. Decisions

=== 8.1 Decided (owner rulings, 2026-11-12)

D0. **Decided 2026-11-12.** Scanners remain external engines behind adapters;
    only the direct CI lanes retire. The adapters call pons-asinorum and
    panic-attack as pinned subprocesses.

D1. **Decided 2026-11-12.** SPECULATIVE pons findings are carried, with an
    explicit evidence class that the grid never grades as blocking. They are
    never dropped and never read as proof.

G1. **Decided 2026-11-12.** pons gates: ponsbot's row is gating, and pons
    `error` keeps its blocking meaning. (Label G1 is this document's own.)

G2. **Decided 2026-11-12.** panic-attack does not gate: panicbot is advisory.
    This overrules the earlier phase-2 note that kept the `PA_GATES`
    block-on-critical behaviour on panicbot's row. (Label G2 is this
    document's own.)
