# Fleet workflow lock-map investigation

Scope: this repository, branch candidate `f8d11228f62abd8784f249995966a449a65c796b` (scanner migration PR #632), compared with main `83e35bcfd04d43960d635fec5397da8dfa344268`. This is not a catalogue or an estate certification. No lock was changed by this investigation.

## Observed coverage

* All **26** current `.github/workflows/*.yml` workflow files have keys in `actions.lock`, both at main and at the candidate. A key is only map coverage, not proof of a runnable workflow or complete closure. There is no observed unmapped workflow to classify as intentionally unmanaged; no owner-approved exception list was supplied.
* Three entries are explicitly empty: `label-triage.yml`, `labels.yml` and `lock-sync-gate.yml`. The workflow YAML contains no `uses` in these files. Their comments describe an intentional no-action design; these are **mapped zero-use workflows**, not missing lock-map entries or evidence of an unmanaged exemption. An empty mapping for a workflow that actually has an action or remote reusable call is a finding.
* The other 23 workflow files have direct external refs and/or a local reusable call; the inventory finds all their directly named external refs in the appropriate workflow map and records for all mapped refs. The local call in `fleet-report-back.yml` points to `fleet-report-back-reusable.yml`, whose own lock entry names its checkout, cache and artifact actions. The local caller's map does not separately list all callee actions. That is a distinction requiring runner/tool semantics, not by itself proof of missing closure. Main run [40933665680](https://github.com/hyperpolymath/gitbot-fleet/actions/runs/40933665680) succeeded; it does not prove every ref or event path was exercised.
* The four remaining standards job-level calls in the candidate are mapped to the existing standards record. The migrated scanner is mapped to a cicd-suite record. Current `gh-actions-lock` [documents](https://github.com/github/gh-actions-lock#limitations) that remote job-level reusable calls are not locked by the tool. Do not infer complete remote closure from the caller map or CLI local verification.
* On this candidate, the pinned scanner source at `hyperpolymath/cicd-suite@4404c3c0474e17753fe7689f3485c02890aac113`, `.github/workflows/secret-scanner-reusable.yml`, was fetched from GitHub and its external `uses` set is `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1`, matching the candidate's suite record and an existing dependency record. The [PR scanner run](https://github.com/hyperpolymath/gitbot-fleet/actions/runs/41227361766) at that candidate created jobs and passed the controls, scan and three contexts. It is not a post-merge run.
* At their **locked commits**, direct composite sources for `deed-ecosystem/validate-action`, `k9-ecosystem/validate-action`, and `smtp-notify-action` have no nested `uses`; `actions/upload-pages-artifact` names `actions/upload-artifact@bbbca2ddaa5d8feaa63e36b76fdaad77386f024f`, which is listed in its record and has a record of its own. These observations do not establish full recursive closure for all other actions, other workflows, or all inputs.
* The earlier fleet report's **4 of 14** map observation (M13/F7) was about the published **cicd-suite** repository, not this repository. Its report separately identifies real regeneration risks here (F2/F3). Neither that observation nor this inventory proves a missing workflow key in fleet.

## Regression coverage added before any further lock edits

`tests/workflow-lock-map-test.py` covers a mapped zero-use workflow, an unexpected missing map, an explicit unmanaged exception (reported as unverified, exit 2), typo exceptions, missing direct action and job-level reusable edges, missing nested records, local reusable coverage at its own path, malformed YAML/ref handling, and an extra workflow edge requiring review. `scripts/audit-workflow-lock-map.py` checks the actual map; it emits findings separately from source-review notes. Its successful exit means only that these map-level checks passed. It cannot detect an edge and its target removed together, discover remote or local composite closure, validate commit/repository identities, or decide whether an extra entry is necessary.

`tests/lock-regeneration-test.py` and `scripts/audit-lock-regeneration.py` separately test comparison to a previously reviewed graph, including dropped composite/reusable edges with no dangling target and malformed ref representations. That comparison cannot establish that the old graph was complete, nor can it review a new pin; it is not an authoritative regeneration or provenance check. Fixtures and the map inventory run in E2E, which already installs PyYAML. They do **not** automatically compare each PR's new lock to the base; PR #631 proposes separate SHA-bound source receipts and broader audit coverage and is still open.

## Not run / decision gate

* Official `gh actions-lock` regeneration and provenance verification were not run: its release asset was inaccessible from this sandbox. No generated lock diff is claimed.
* No complete, recursive source inventory and provenance verification for **all** transitive dependencies was performed; no owner-confirmed intentionally unmanaged workflows were identified. The possibility of a missing closure outside the specific sources above remains open.
* Before any further lock regeneration, review source-derived SHA-bound closure (including local composites and reusable workflow subpaths), run the separate dropped-closure checks with a reviewed baseline, use the official tooling where available, and validate actual runner startup. Do not rewrite pinned tag refs or immutable resolutions merely to make a check pass. Coordinate with PR #631 rather than treating this map inventory or the catalogue as a fix.
