= Retired learning-loop rules: what they detected and where that went
:toc:

== Status

The rule files of the learning loop were written in a rule language that the
estate has retired. They were removed in the change that added this record.
Hypatia's rule system is pure Elixir (`lib/rules/*.ex` in
`hyperpolymath/hypatia`), so no rule here was ported as a new rule file; this
record states, for each one, what it matched and which Hypatia rule covers it
today. It is a record, not a source of rules: do not translate it back into a
rule file.

The removed files are recoverable from git history. Last commit that carried
them: `dec1e7ce36dfa62ea121b530108de04cc8321e69` (gitbot-fleet `main`).
Hypatia coverage was read from Hypatia `main` at `6f3f16f` on 2026-11-17 by
reading `lib/rules/code_safety.ex`, `lib/rules/cicd_rules.ex` and
`lib/rules/honest_completion.ex`. No rule was run to check it.

Nothing consumed these files except the generator and report code removed in
the same change. The only publication path (opening rule PRs in Hypatia and
enabling auto-merge) sat behind the quarantine in
`docs/AUTOMATION-QUARANTINE.adoc`, and the workflow job that would have
deployed approved rules (`deploy-approved-rules`) is disabled with `if: false`.

== Approved rules (three)

All three were approved on 2026-02-06 with a validation score of 92% and
recorded in `rule-deployment-status.json`. Each carried the same detector
shape: a `has_issue` check, a severity, a fix suggestion and an
`auto_fixable` flag set to false.

[cols="1,3,3",options="header"]
|===
|Rule (object name) |What it matched and flagged |Hypatia coverage

|`eval_usage` (`eval_usage_detector`); 7 observations; CWE-95
|In `.js`, `.jsx`, `.res`, `.mjs` and `.cjs` files, outside `//` comments and
double-quoted strings: a call to `eval(`; `Function(` or `new Function(`; and
`setTimeout(` or `setInterval(` with a double-quoted string argument.
Severity critical in production code, high in test code (paths with `/test/`,
`/tests/`, `/__tests__/`, `.test.js`, `.spec.js`); tool paths (`/scripts/`,
`/tools/`, `/build/`, `webpack.config`, `rollup.config`) did not count as
production. Also suggested a Content-Security-Policy header
(`script-src 'self'; object-src 'none'`) when no CSP protection was found.
|*Partial.* `js_eval` in `lib/rules/code_safety.ex` (critical, CWE-94, pattern
`\beval\s*\(`) covers direct `eval(`. *No Hypatia rule* covers the `Function`
constructor or string arguments to `setTimeout`/`setInterval`, the
test/production severity split, or the CSP recommendation.

|`technical_debt` (`technical_debt_detector`); 196 observations; CWE-1057
|In any source file, the markers `TODO:`, `FIXME:`, `HACK:`, `XXX:` and `BUG:`
with the text after the marker. Severity info. Triage priority by marker: BUG
critical, FIXME high, HACK medium, TODO and XXX low. A repository with more
than 50 markers was flagged as excessive debt. The suggested fix was to open a
GitHub issue carrying the priority and message.
|*Partial.* `lib/rules/honest_completion.ex` counts `TODO` and `FIXME`
repository-wide and reports when TODOs exceed 50 or FIXMEs exceed 20.
`baseline_health.ex` BH002 flags a deferred-migration TODO in a manifest. *No
Hypatia rule* matches `HACK:`, `XXX:` or `BUG:`, emits a finding per marker,
or assigns the per-marker priority.

|`unsafe_without_doc` (`unsafe_without_doc_detector`); 19 observations;
CWE-1188
|In `.rs` files, an `unsafe` token followed by `{` on the same line, with no
safety comment one or two lines above. A safety comment was a `//` line
containing `SAFETY:`, `Safety:`, `safe because`, `invariant`, `guarantee`,
`rationale` or `reason` (or their capitalised forms). Severity high, critical
in production code (not under `/test/`, `/tests/`, or `_test.rs`). Suggested
adding a `// SAFETY:` comment.
|*Covered.* `unsafe_block` in `lib/rules/code_safety.ex` (medium, CWE-676,
pattern `unsafe\s*\{`) with `reject_excused_unsafe`, which drops a match that
has a `SAFETY:` comment directly above it or sits inside a string. Differences:
Hypatia's severity is medium with no production escalation, and it accepts only
a `SAFETY:` comment, not the looser keywords the retired rule accepted.
|===

The approval metadata beside each approved rule (`status: approved`,
`approved_by: ECHIDNA Semantic Validation v1.0`, `validation_score: 92%`,
`production_ready: true`, with the observation count and the dates
2026-02-06) was removed with it. The same facts are in
`rule-deployment-status.json`, which is kept.

== Proposals that were never approved (seven files, four distinct rules)

* `eval_usage`, `technical_debt` and `unsafe_without_doc`: byte-identical to the
  approved rules above.
* `getexn_on_external_data` (6 observations, 2026-01-25): a draft that matched a
  line containing the literal text `getexn_on_external_data` and rated it high.
  It was malformed (a bare `LineNum` goal) and carried a TODO to merge it into a
  rule file that is not in this repository. The intent, ReScript `getExn` on
  external data, is covered by `getexn_on_external` in
  `lib/rules/code_safety.ex` (critical, CWE-754, pattern `getExn`).
* `type_safety_bypass` (5 observations), `unsafe_crash` (8) and `unsafe_panic`
  (15): generic stubs generated 2026-02-06. Each had a detection clause that
  ended in `fail`, so none could ever report anything, plus a medium severity
  and a "manual review required" suggestion. *There is no detection content to
  port.* They record only that these three pattern types were observed.

`rule-deployment-status.json` lists `unsafe_panic`, `type_safety_bypass`,
`unsafe_crash` and `cors_misconfiguration` as approved with quality `template`
or `auto-fix`. The first three are the stubs above. No rule file for
`cors_misconfiguration` existed in the tree.

== Glambot findings bridge

The glambot findings bridge (`bots/glambot/bot-integration/src/glambot_findings`, removed;
nothing loaded it) was a design for turning glambot presentation findings into
facts. Its JSON ingestion was a placeholder that printed "JSON parsing requires
FFI integration" and returned no findings, so it never ran against real data.
Finding categories: visual (`VIS-*`), accessibility (`ACC-*`), SEO (`SEO-*`),
machine-readability (`MACH-*`) and git-SEO (`GS-*`).

Its derived checks, none of which has a Hypatia rule:

* presentation debt: a repository with more than 5 findings; a sustainabot
  alert when it has more than 10;
* fleet-wide pattern: the same rule id firing in 3 or more repositories;
* low-hanging fruit: findings marked fixable;
* accessibility regression: any accessibility finding of severity error;
* SEO coverage gap: any SEO finding;
* finishbot trigger: any glambot finding of severity error, "blocks release";
* fix success rate per rule id: successes divided by recorded outcomes.

Hypatia has no glambot or presentation rule (a search of `lib/` for
`glambot`, `presentation` and `accessib` found none in `lib/rules/`).
glambot's own findings still reach the fleet through the Rust
`shared-context` library; only this aggregation layer is retired.
